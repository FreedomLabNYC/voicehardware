# M5StickS3 Hermes relay + stick bring-up

Project: the `m5sticks3-hermes-relay` tree — ESP32-S3 stick <-> relay (ws :8792) <-> cloud STT/TTS via .env MODEL_SERVING_ENDPOINT (api.openai.com) <-> Hermes dashboard (:9119) -> gateway (:18789). Relay normally runs in Docker (`m5-hermes-relay`, compose project `m5-hermes`); native fallback below when docker group access is broken.

## Service start order (all must be up; none auto-start)
1. `hermes dashboard --host 0.0.0.0 --port 9119 --no-open` (background; relay logs in as admin via /auth/password-login using the .env credentials).
2. Relay, either mode:
   - Docker: `docker compose up -d relay` from `relay/` (foreground terminal tool BLOCKS this string — run via terminal(background=true)); verify `docker compose ps` Up+healthy.
   - Native (no docker group needed; relay deps are just httpx + websockets, both in system python3): `cd relay && set -a && . ../.env && set +a && export HERMES_DASHBOARD_URL=http://127.0.0.1:9119 && python3 hermes_relay.py 2>&1 | tee -a ~/m5-relay.log` (background). Before starting, apply the docker-only .env fixes: empty `VOICECHAT_REF_AUDIO=` and a working `MODEL_SERVING_API_KEY` (see pitfalls).
3. Verify log lines "authenticated with the dashboard" + "relay listening on ws://0.0.0.0:8792"; `ss -tln | grep 8792`.
4. Firewall: inbound :8792 from the stick's subnet must pass (see ufw pitfall) — a healthy relay with zero stick traffic is usually this.
5. Reset the stick (RTS pulse or unplug/replug); expect `stick connected from 192.168.1.x` in the relay log within ~30-90 s. A `stick connected from 127.0.0.1` session is a local diagnostic/test client — never treat it as proof the physical stick works.

## Pitfalls (each cost real time)
- `dashboard sign in failed` / "not the Hermes dashboard (HTTP 404)" on an address ending `:8765` = the URL field was given the gadget WebSocket listener, which serves only `ws://…:8765/gadget` and answers plain HTTP with a deliberate 404. Dashboard-authenticated tools want the HTTP dashboard instead: `http://<host-ip>:9119` (LAN), `http://127.0.0.1:9119` (native), `http://172.17.0.1:9119` (inside Docker). The dashboard is a SEPARATE process from the gateway service — `systemctl --user status hermes-gateway` running does not mean :9119 answers; check `ss -tln | grep 9119`, start it per step 1, and verify with `curl -s -o /dev/null -w '%{http_code}' http://<host>:9119/` (302 = sign-in redirect = alive).
- `host.docker.internal` does NOT resolve inside this container even with extra_hosts — use `http://172.17.0.1:<port>` for host services in .env (MODEL_SERVING_ENDPOINT, HERMES_DASHBOARD_URL).
- `MODEL_SERVING_API_KEY` in the repo .env can be REVOKED — the startup warmup then dies with HTTP 401 on /audio/transcriptions. Validate without echoing the secret: `curl -o /dev/null -w '%{http_code}' -H "Authorization: Bearer $KEY" https://api.openai.com/v1/models` (200 = live). A current key is `OPENAI_API_KEY` in `~/.hermes/.env`; repo `.env` is gitignored — swap it in place with sed. Empty `MODEL_SERVING_API_KEY=` likewise crashes startup (require() fails).
- Stick screen "LINK" = Connecting state, NOT connected. Connected shows idle text "hold M5". TWO distinct reject signatures in relay logs: `connection rejected (200 OK)` every ~30 s = the OLD superseded stick (stale test-network build) knocking — ignore it; `rejecting <ip>: bad or missing device key` every 2-4 s = a stick reaching the relay with baked-in RELAY_KEY != container's HERMES_STICK_DEVICE_KEY. Before blaming keys, PROVE all three sides byte-identical: .env value vs `strings -a firmware/.pio/build/m5sticks3/src/main.cpp.o` vs `docker compose exec relay python -c "import os;print(os.environ.get('HERMES_STICK_DEVICE_KEY',''))"`. If they all match, the rejections are NOT your live stick — likely the sibling voicechat stick sharing the IP — and the real fault is elsewhere (see keepalive drop). Fix when keys genuinely differ: rebuild firmware against repo-root .env (load_env.py bakes key+host at compile time).
- Crash-loop root cause is usually upstream: relay exits at login if dashboard :9119 is down. Check `docker inspect -f '{{.State.Status}} {{.RestartCount}}' m5-hermes-relay` + `ss -tlnp | grep 9119`; start dashboard first, container self-heals via unless-stopped (no restart needed).
- KEEPALIVE DROP: relay pings ws clients every 20 s; the Arduino WebSockets client only answers pings inside `loop()`, and `loop()` early-returns in a `delay(20)` poll while `asleep` (display sleep after 5 s idle). A sleeping stick gets dropped ~40 s after connecting (`stick disconnected`, no stick-side serial) and can take minutes to redial. To watch a live session: serial-capture /dev/ttyACM1 AND reset the stick (RTS pulse via pyserial, or unplug/replug) so boot lands inside the capture window.
- Required stack is only dashboard :9119 + gateway + relay (compose run from `relay/`); the relay reaches the gateway through the dashboard's `/api/ws` proxy — `ss -tln` showing only 9119 + 8792 listening is HEALTHY, do not chase a separate :18789 listener. This repo has no local whisper_api — STT/TTS are cloud via .env MODEL_SERVING_ENDPOINT.
- `.env` WIFI fields drift: they sat at the old test-SSID/credentials while the sticks
  lived on the real home network. Keep your current SSID+password ONLY in your own
  `.env` (never in docs or commits). load_env prints what it bakes at build start —
  read it before flashing.
- Verify baked firmware values WITHOUT reflashing: `strings -a .pio/build/m5sticks3/src/main.cpp.o` (check .o timestamp). PlatformIO skips recompiling main.cpp when only build_flags change — force with `-t clean`.
- Always cross-check the extracted baked relay host/IP against this machine's CURRENT address (`ip -4 addr show`): after a DHCP change or a Wi-Fi→wired move the stick dials a stale address and this machine sees zero trace of it (no connection, no reject, no UFW BLOCK) — looks identical to every other silent fault. The stick dials only the compiled-in IP; the relay's 0.0.0.0 binding does not help if the address itself changed.
- Voice cloning is incompatible with cloud tts-1: a non-empty `VOICECHAT_REF_AUDIO` makes the startup warmup transcribe the reference and then send `ref_audio` while leaving `voice` empty — OpenAI rejects with 400 `body -> voice field required` (mid-session, after STT+Hermes already worked), and native runs `sys.exit` when the relative `./voice.mp3` doesn't exist in cwd. For the OpenAI path set `VOICECHAT_REF_AUDIO=` (empty) and `VOICECHAT_TTS_VOICE=nova`. Cloning needs a self-hosted Base-checkpoint TTS (e.g. Qwen3 TTS-1.7B); none exists on the LAN (Spark serves only ollama, no /audio endpoints).
- ufw silently blocks the stick: with ZERO `stick connected` AND zero reject lines in the relay log, check the firewall before WiFi or keys — `systemctl is-active ufw`, then read (world-readable) `/etc/ufw/ufw.conf` ENABLED, `/etc/default/ufw` DEFAULT_INPUT_POLICY, and grep `--dport` in `/etc/ufw/user.rules`. A reboot re-enables DROP-incoming and the stick's 8792 attempts vanish without a trace. Unblocking (`sudo ufw allow 8792/tcp`) and group fixes (`sudo usermod -aG uucp,docker <your-user>`) are user-password actions. AFTER the port is open, if `stick connected` still never appears, discriminate by kernel journal: `journalctl -k --since "<plug time>" --no-pager | grep DPT=8792` — `[UFW BLOCK] ... DPT=8792` lines = rule not effective (or machine rebooted); ZERO block lines AND zero connections = the stick's packets never reach this machine — that is WiFi/sleep/unflashed firmware, not firewall, keys, or relay. Next probe: `ip neigh | grep -i <stick-MAC>` (net-tools `arp` is not installed on Omarchy) — no ARP entry means the stick is absent from the LAN. Before reflashing, ask the user to read the stick screen: `LINK` = stuck joining WiFi, `hold M5` = claims connected, blank = press KEY1 to wake, still blank = possibly flashed empty. `sg` (shadow) is NOT installed on the Omarchy host — the old `sg uucp`/`sg docker` no-re-login trick does not exist there; use the setfacl route below instead.
- Docker group drift: PermissionError on /var/run/docker.sock means the user is not in `docker` (verify with `groups`) — don't debug docker, use the native relay start.
- Serial needs `uucp` membership (/dev/ttyACM* is root:uucp 660 -> PermissionError) and group grants do NOT survive an OS reinstall/migration — verify with `groups` rather than assuming. Fastest fix without re-login (no `sg` on Arch hosts): user runs `sudo setfacl -m u:<your-user>:rw /dev/ttyACM<N>` — immediate; the ACL is lost when the device node is recreated, so repeat after every replug. pyserial is absent from system python — `python3 -m venv <scratch>/serialenv && <scratch>/serialenv/bin/pip install pyserial` and run scripts/serial_capture.py + scripts/reset_stick.py with that venv's python. serial_capture buffers and only writes its file at the END of the capture window — send the reset pulse right after the capture opens.
- Native-USB ESP32-S3 (idProduct 1001, USB JTAG/serial): hammering esptool while BOOT-held FAILS — the app keeps grabbing the CDC endpoint. What worked: user holds BOOT, plugs USB, holds ~3-5 s, releases; device then enumerates and download mode is reachable on whichever ttyACM appears (ports swap between sticks — check `journalctl -k` serial number/MAC to identify which stick got which port). This stick flashed on ttyACM1; identify each device by its kernel-log serial, never by a hardcoded MAC.
- After erase_flash + upload, stick boots but serial prints NOTHING until KEY1 (small side button near strap loop — same one used for BOOT) wakes it from 5 s idle sleep. Always have user press it before reading console.
- Sibling `m5-stick-voicechat` repo holds the old local whisper_api.py (:8793, whisper tiny + piper at `~/.local/share/piper/en_US-lessac-medium.onnx`, no espeak binary). Its bug class: FastAPI Form param named `model` shadowed the loaded model global -> `'str' object has no attribute 'transcribe'` (global is `_whisper_model`); `PiperVoice.synthesize_wav` needs a `wave.open()` wrapper, not a raw file handle.
- Pure-tone/beep test audio transcribes to empty -> relay says "didn't catch that"; the repo's voice.mp3 is a beep (its clone ref-text transcribes as "Beep."). For E2E tests generate real speech via POST /audio/speech, convert with `ffmpeg -ar 16000 -ac 1 -f s16le`, and feed the raw PCM as the utterance.
- Wi-Fi: the stick joins the home network and takes whatever DHCP lease it gets, and
  the PC's LAN IP can change (Wi-Fi lease vs wired lease) — the relay listens on
  0.0.0.0 so the binding is never the problem; the .env HERMES_STICK_RELAY_HOST must
  match what's BAKED into firmware (compile-time define via load_env.py reading the
  repo-root .env).

## End-to-end test without the stick
websockets connect `ws://<host-ip>:8792/?key=$KEY` (127.0.0.1 works when testing the relay itself) -> expect ready+idle("hold M5") -> send `{"type":"start"}` -> stream PCM 4096-B chunks -> `{"type":"end"}` -> expect transcript/reply/audio_start/BIN.../audio_end/idle. DIAGNOSTIC: transcript + reply with AUDIO_BYTES=0 means only the TTS leg is broken — not STT, not the Hermes brain, not the stick path. Full turn verified end to end from loopback against the native relay.
